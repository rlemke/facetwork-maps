Do variant-caller validations survive a benchmark update?

A reproduction study of NIST Genome in a Bottle HG001 releases v3.3.2 and v4.2.1, run as a Facetwork FFL workflow. September 2026.

1. Purpose of the analysis

Genome in a Bottle (GIAB) is the reference truth set used worldwide to validate germline variant callers. A laboratory measures its caller's sensitivity and precision by comparing calls against a GIAB benchmark VCF restricted to GIAB's high-confidence regions.

NIST periodically publishes new benchmark releases. That creates a practical question with real consequences for any lab that has already validated:

If a caller was validated against HG001 v3.3.2, does that validation still hold on v4.2.1 — and if not, exactly where does it stop holding?

Answering it requires knowing not just how many variants changed, but which kind of claim changed: whether the sites themselves moved, or only the genotype evidence attached to them. Those imply different remediation.

Scope, stated plainly. This study compares two published NIST releases against each other. It does not re-execute GIAB's benchmark-construction pipeline, which integrates multiple sequencing platforms and callers over ~100 GB of reads. No claim is made here about reproducing NIST's methodology. What is reproduced is the comparison, and what is new is its characterisation.

2. What the published work reports

NIST's own description of the v4 series is that it substantially expanded the high-confidence regions over v3, by incorporating additional sequencing technologies and improved integration methods, and that genotype representation was revised. The published artifacts corroborate the expansion directly:

Published artifactv3.3.2v4.2.1change
benchmark VCF (GRCh38, gzipped)107.1 MB125.9 MB+17.6%
high-confidence region BED10.5 MB15.5 MB+47.6%

The BED file defines where the benchmark makes a claim at all. A ~48% larger region file is the published evidence for the stated expansion. What the release artifacts do not state, and what a validating lab actually needs, is the per-variant consequence.

Why every genotype differs

The genotype column differs for every shared variant, in three distinct ways at once. A representative record:

chr1:817186 G>A
  v3.3.2  FORMAT=GT:DP:ADALL:AD:GQ:IGT:IPS:PS   1|1:823:0,381:78,454:283:1/1:.:PATMAT
  v4.2.1  FORMAT=GT:PS:DP:ADALL:AD:GQ           1/1:.:1041:78,459:0,88:348
  1. FORMAT restructured — IGT and IPS dropped, PS moved forward.
  2. Phasing dropped — 1|1 became 1/1.
  3. Evidence values genuinely increased — depth 823 → 1041, genotype quality 283 → 348. This is not reformatting; v4.2.1 rests on more data.

The operational answer

Site-level validation carries over. Genotype-level validation does not. A lab measuring sensitivity/precision on variant sites can rely on its v3.3.2 work for the shared set and needs only to evaluate the 516,828 added sites. A lab whose acceptance criteria touch genotype quality, depth, or phasing must re-run in full: every one of those records changed.

The algorithmic difference that matters

The conventional comparison for this task is a checksum or a diff, and both give the wrong answer here. A checksum reports failed; a naive diff reports every record as changed. Neither distinguishes "the sites are identical and only the genotype encoding moved" from "the calls disagree" — yet those demand opposite responses.

Our comparison instead reports the highest level at which two outputs agree:

exists → schema → cardinality → keys → values → bytes

and, critically, reports every normalisation required to reach that level. Sorting keys or applying a tolerance until two files match does not demonstrate a reproduction — it manufactures one — so each is declared in the result rather than hidden inside it.

This design came from an earlier measurement, not from theory. Reproducing PyPSA grid-builder's output, two orchestrators produced byte-different files containing identical data, because the upstream tool serialises a nested dictionary in unstable key order. Bytes differ; the data does not. Any comparison that cannot express that distinction will misreport a correct reproduction as a failure.

Scale

The comparison indexes one file at a time into a compact digest map rather than materialising records, so peak memory tracks the key count rather than the file size — 1.0 GB where the naive implementation required 5.4 GB for the same inputs. That is what allows a whole-genome benchmark comparison to run on an ordinary fleet node.

5. Reproducing this

The workflow is 60 lines of FFL composed entirely from built-in facets — no domain-specific handlers. fw.http.Fetch acquires each published release and records its digest and provenance; fw.compare.Tabular compares; fw.compare.Summarise documents.

fw ffl run --primary examples/repro-giab/giab_benchmark_diff.ffl \
           --workflow repro.giab.CompareBenchmarkReleases

6. Limitations

  • Counts are over the complete GRCh38 benchmarks. An earlier draft of this page reported figures from a partial slice; the pattern held but the absolute numbers did not — the slice was chromosome-1 heavy, which under-counted added sites by more than threefold (154,863 vs 516,828). The slice figures have been replaced.
  • GIAB's methodology is not re-executed, so this cannot detect an error in the benchmark construction itself — only differences between two published outputs.
  • Comparison is by exact variant identity. Two releases representing the same biological variant differently (left-alignment, MNP decomposition) would appear as one retired and one added record. Normalisation of representation is a known extension and is not applied here.
